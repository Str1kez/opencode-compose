# opencode-compose

Поднимает сервер opencode v2 в контейнере на Debian slim. С ним работаешь из браузера на хосте. Я сделал это для мака, на котором бинарник opencode запустить нельзя: MDM помечает его и убивает при старте. Docker при этом работает, так что opencode живёт в контейнере, а наружу торчит только веб-интерфейс на `127.0.0.1`.

Что внутри:

- рабочий репозиторий монтируется на запись по тому же абсолютному пути, что и на хосте;
- `~/.config/opencode` и `~/.gitconfig` хоста монтируются только на чтение;
- сервер слушает `0.0.0.0:4096` внутри контейнера и закрыт паролем (HTTP basic auth);
- раз в сутки контейнер проверяет новую версию opencode, ставит её и перезапускается.

## Что нужно

- Docker-движок и `docker compose` v2. Подойдёт любой: colima, OrbStack, Docker Desktop. Визард определяет движок сам. Я рекомендую colima: она бесплатная, без GUI и ведёт себя предсказуемо;
- `~/.config/opencode` и `~/.gitconfig` на хосте (если их нет, compose упадёт с понятной ошибкой, а не создаст пустую папку).

### Установка colima

```sh
brew install colima docker docker-compose
colima start
```

Плагин `docker-compose` brew просит подключить отдельно: следуй его сообщению после установки. Если colima уже стоит и запущена, визард её подхватит.

### Подвох colima: репозиторий вне домашней папки

colima пробрасывает в свою VM только смонтированные папки, по умолчанию `$HOME` на запись. Если `WORKSPACE` лежит внутри `$HOME`, ничего делать не надо: хватит `colima start`. Если снаружи, контейнер увидит пустую папку, а не репозиторий. Визард это проверяет и печатает нужную команду:

```sh
colima start --mount /opt/work/my-repo:w --mount $HOME:w
```

`--mount` заменяет весь список mount, поэтому `$HOME:w` в команде остаётся: там конфиги, которые нужны контейнеру, а запись в домашнюю папку нужна твоим остальным контейнерам в этой VM. Репозиторий внутри `$HOME` отдельным mount не передавай: colima откажется стартовать с ошибкой `overlapping mounts not supported`. Если у тебя в colima есть свои mount, допиши их сам. Перезапуск colima останавливает все контейнеры в VM, не только opencode. Визард запускает команду только после твоего подтверждения. На OrbStack и Docker Desktop этой проблемы нет.

## Запуск через визард (самый кайф)

```sh
make
```

Визард проверяет Docker и конфиги, спрашивает путь к репозиторию (на colima проверяет, что он виден в VM), предлагает питон-профиль и git-доступ, генерирует пароль, пишет `.env` и `docker-compose.override.yml`, собирает и поднимает контейнер, а в конце открывает браузер с паролем в буфере обмена. Его можно перезапускать: уже сохранённые значения он предлагает по Enter. Это касается и вопросов да/нет: если git push по ssh или питон-профиль включены, Enter оставляет их включёнными (`[Y/n]`). Движок визард тоже запоминает (`DOCKER_ENGINE` в `.env`). Если docker сейчас смотрит в другой движок, чем в прошлый раз, или контекстов несколько, он спросит, какой взять, и предложит прошлый.

## Запуск руками

```sh
cp .env.example .env
```

В `.env` заполни минимум две переменные:

```sh
WORKSPACE=/Users/me/work/my-repo
OPENCODE_SERVER_PASSWORD=<вывод openssl rand -base64 32>
```

Если Docker Hub недоступен или тормозит, укажи в `.env` Debian-образ, который уже лежит локально, например `BASE_IMAGE=debian:bookworm-slim`.

```sh
docker compose up -d --build
docker compose logs -f
```

При первом старте контейнер скачивает opencode с npm, это может занять несколько минут. Готовый сервер пишет в лог:

```
[opencode-update] 2026-11-10 00:17:33 installing opencode 2.2.6
[opencode-update] 2026-11-10 00:17:42 next update check in 13338s (daily at 4:00 Europe/Moscow)
server listening on http://0.0.0.0:4096
```

Открой `http://localhost:4096`. Браузер спросит логин и пароль: логин `opencode`, пароль из `OPENCODE_SERVER_PASSWORD`.

## Провайдеры моделей

В `opencode.jsonc` лежат настройки провайдеров: адреса, заголовки, модели. Ключи и OAuth-токены, полученные через `opencode auth login`, opencode v2 хранит в своей базе (`~/.local/share/opencode/opencode.db`), и с хоста они не подтянутся. Если ключ подключён в конфиге через `{file:...}` из папки конфига, он работает и в контейнере. Ключ через `{env:...}` заработает, только если добавить эту переменную в `environment` в `docker-compose.override.yml`: переменные хоста в контейнер сами не попадают. Иначе залогинься один раз в веб-интерфейсе или через CLI внутри контейнера:

```sh
docker compose exec opencode opencode auth login --server http://127.0.0.1:4096
```

Логин сохраняется в volume `opencode-home` и переживает перезапуски и обновления.

Любую команду opencode внутри контейнера запускай с `--server http://127.0.0.1:4096`. Без этого флага CLI поднимет второй, фоновый сервер со своими настройками.

## Git-доступ

Чтобы агент делал `git push` из контейнера, нужен ключ без passphrase: ssh-agent в контейнере нет, ввести passphrase некому. Не бери для этого свой личный ключ. Заведи отдельный deploy-ключ:

```sh
ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_deploy
```

Публичную часть `~/.ssh/id_deploy.pub` добавь в GitLab: в проекте `Settings > Repository > Deploy keys`, с галочкой `Grant write permissions`. Без неё push отвергнут.

Визард (стадия «Git-доступ по SSH») показывает приватные ключи из `~/.ssh`. Если на выбранном стоит passphrase, он не даёт его взять и возвращает к выбору ключа: пропустить стадию можно, введя `-`. Путь к ключу он делает абсолютным и отвергает пути с `"`, `\`, `$`, `:` и переводами строк, иначе они ломают mount. Хост он берёт из remote репозитория и собирает known_hosts через `ssh-keyscan`. Тут нужно сверить fingerprint с тем, что публикует провайдер или говорит админ сервера: знакомство с хостом без сверки не защищает от подмены. known_hosts лежит в `.git-ssh/` (она в `.gitignore`). Ключ и known_hosts монтируются в контейнер только на чтение, git ходит ими через `GIT_SSH_COMMAND` (с `BatchMode=yes`: если ключ не подошёл, git падает сразу, а не ждёт ввода). `~/.gitconfig` хоста не мешает.

В `.env` визард пишет `GIT_SSH_COMMAND` только после того, как записал `docker-compose.override.yml` с mount ключа. Если ты отказался перезаписать override, старая настройка остаётся как была, а в итоговом списке появится строка, что ssh-изменение не применено.

Когда сервер поднялся, визард делает из контейнера `git push --dry-run` и показывает результат. Ошибка не останавливает визард, это только проверка.

Поддержан только push по ssh. Remote по https визард пропускает. Remote через псевдоним из `~/.ssh/config` (`git@gl-work:group/repo.git`) тоже не поддержан: в контейнере этого конфига нет, и псевдоним там не разрешится. Визард узнаёт такой remote через `ssh -G`, печатает готовую команду `git remote set-url` с настоящим хостом и пропускает стадию.

## Тулчейн проекта

В образе есть только то, что нужно самому opencode: git, curl, ripgrep. Чтобы агент собирал проект и гонял тесты, нужен ещё тулчейн проекта.

Для питона есть профиль, его включает визард (`INSTALL_UV=1` в `.env`): `uv` ставится прямо в образ. Компилятор `build-essential` визард подставляет как значение `EXTRA_APT_PACKAGES` по умолчанию. Системного питона в образе нет: нужную версию приносит `uv sync`. Dev-библиотеки для нативных зависимостей допиши в `EXTRA_APT_PACKAGES`, например `build-essential libpq-dev libffi-dev`, и пересобери образ.

У контейнера свой `.venv`: отдельный volume смонтирован поверх `WORKSPACE/.venv`. Хостовый venv собран под macOS и в Linux бесполезен, поэтому контейнер его не видит и не перезаписывает, а твой `uv sync` на хосте не ломает контейнерный. Volume свой для каждого репозитория: визард пишет в `.env` имя `VENV_VOLUME` вида `opencode-venv-<хвост пути>-<контрольная сумма>`. Если сменить `WORKSPACE` и оставить старый `VENV_VOLUME`, контейнер возьмёт чужой venv, поэтому при ручной смене репозитория меняй и его. Без `VENV_VOLUME` volume называется `opencode-venv`.

На хосте в `WORKSPACE` остаётся пустая папка `.venv`, даже если проект не на питоне: это точка монтирования. Визард создаёт её сам. Если запускаешь без визарда, сделай `mkdir .venv` в репозитории заранее, иначе на Linux Docker создаст папку от root. Подробности в `docs/adr/0003-container-venv-isolated-from-host.md`.

Для остальных стеков перечисли системные пакеты в `EXTRA_APT_PACKAGES` в `.env` и пересобери образ:

```sh
EXTRA_APT_PACKAGES=build-essential libpq-dev
```

В домашнюю папку агент может ставить что угодно (`nvm`, Python через `uv python install`, свои бинарники). Она лежит в volume `opencode-home`, поэтому установленное переживает перезапуски и обновления.

## Обновления

В 4:00 по `TZ` контейнер сверяет установленную версию с последней. Если вышла новая, он ставит её и перезапускается сам. Если версия та же, ничего не происходит. Час задаёт `OPENCODE_UPDATE_HOUR`. Перезапуск обрывает агента, если тот в этот момент работает.

Проверить и обновить руками:

```sh
docker compose exec opencode opencode-update check
docker compose restart
```

## Тонкие места

- Абсолютные симлинки в `~/.config/opencode` (например, `plugins -> ~/dotfiles/...`) в контейнере никуда не ведут. Контейнер перечисляет их при старте строками `warning: broken symlink`. Цель такой ссылки надо смонтировать по тому же пути, пример лежит в `docker-compose.override.yml.example`. Туда же можно добавить глобальные скиллы из `~/.agents`.
- `127.0.0.1` и `localhost` в конфиге opencode внутри контейнера означают сам контейнер. Если провайдер или MCP ходит в локальный прокси на хосте, впиши его порт в `HOST_LOOPBACK_PORTS` в `.env` (визард находит такие порты в конфиге сам). Контейнер пробросит `localhost:<порт>` на тот же порт хоста, и конфиг менять не придётся.
- `include` и `includeIf` в `~/.gitconfig` ссылаются на файлы, которых в контейнере нет. Если git в контейнере не знает `user.name`, смонтируй эти файлы через override.
- На Linux-хосте поставь в `.env` `OPENCODE_UID` и `OPENCODE_GID` из `id -u` и `id -g`, иначе файлы в репозитории будут принадлежать чужому пользователю. На маке это не нужно.
