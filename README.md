# opencode-compose

Поднимает сервер opencode v2 в контейнере на Debian slim. С ним работаешь из браузера на хосте. Я сделал это для мака, на котором бинарник opencode запустить нельзя: MDM помечает его и убивает при старте. Docker при этом работает, так что opencode живёт в контейнере, а наружу торчит только веб-интерфейс на `127.0.0.1`.

Что внутри:

- рабочая папка (один репозиторий или папка с несколькими) монтируется на запись по тому же абсолютному пути, что и на хосте;
- `~/.config/opencode` и `~/.gitconfig` хоста монтируются только на чтение;
- сервер слушает `0.0.0.0:4096` внутри контейнера и закрыт паролем (HTTP basic auth);
- раз в сутки контейнер проверяет новую версию opencode, ставит её и перезапускается.

## Что нужно

- Docker-движок и `docker compose` v2. Подойдёт любой: colima, OrbStack, Docker Desktop. Визард определяет движок сам. Я рекомендую colima: она бесплатная, без GUI и ведёт себя предсказуемо;
- `~/.config/opencode` и `~/.gitconfig` на хосте (если их нет, compose упадёт с понятной ошибкой, а не создаст пустую папку).

### Установка colima

```sh
brew install colima docker docker-compose
colima start
```

Плагин `docker-compose` brew просит подключить отдельно: следуй его сообщению после установки. Если colima уже стоит и запущена, визард её подхватит.

### Подвох colima: рабочая папка вне домашней папки

colima пробрасывает в свою VM только смонтированные папки, по умолчанию `$HOME` на запись. Если `WORKSPACE` лежит внутри `$HOME`, ничего делать не надо: хватит `colima start`. Если снаружи, контейнер увидит пустую папку, а не твой код. Визард это проверяет и печатает нужную команду:

```sh
colima start --mount /opt/work:w --mount $HOME:w
```

`--mount` заменяет весь список mount, поэтому `$HOME:w` в команде остаётся: там конфиги, которые нужны контейнеру, а запись в домашнюю папку нужна твоим остальным контейнерам в этой VM. Рабочую папку внутри `$HOME` отдельным mount не передавай: colima откажется стартовать с ошибкой `overlapping mounts not supported`. Если у тебя в colima есть свои mount, допиши их сам. Перезапуск colima останавливает все контейнеры в VM, не только opencode. Визард запускает команду только после твоего подтверждения. На OrbStack и Docker Desktop этой проблемы нет.

## Запуск через визард (самый кайф)

```sh
make
```

Визард проверяет Docker и конфиги, спрашивает рабочую папку (на colima проверяет, что она видна в VM), предлагает питон-профиль и git-доступ, генерирует пароль, пишет `.env` и `docker-compose.override.yml`, собирает и поднимает контейнер, а в конце открывает браузер с паролем в буфере обмена. Его можно перезапускать: уже сохранённые значения он предлагает по Enter. Это касается и вопросов да/нет: если git push по ssh или питон-профиль включены, Enter оставляет их включёнными (`[Y/n]`). Движок визард тоже запоминает (`DOCKER_ENGINE` в `.env`). Если docker сейчас смотрит в другой движок, чем в прошлый раз, или контекстов несколько, он спросит, какой взять, и предложит прошлый.

## Запуск руками

```sh
cp .env.example .env
```

В `.env` заполни минимум две переменные:

```sh
WORKSPACE=/Users/me/work
OPENCODE_SERVER_PASSWORD=<вывод openssl rand -base64 32>
```

Если Docker Hub недоступен или тормозит, укажи в `.env` Debian-образ, который уже лежит локально, например `BASE_IMAGE=debian:bookworm-slim`.

```sh
docker compose up -d --build
docker compose logs -f
```

`--env-file` не нужен: compose сам читает `.env` из папки проекта и подставляет оттуда `WORKSPACE`, `INSTALL_UV` и остальное, включая аргументы сборки. Переменная, экспортированная в шелле, перебивает значение из `.env`. Посмотреть, что в итоге получилось, можно командой `docker compose config`.

При первом старте контейнер скачивает opencode с npm, это может занять несколько минут. Готовый сервер пишет в лог:

```
[opencode-update] 2026-11-10 00:17:33 installing opencode 2.2.6
[opencode-update] 2026-11-10 00:17:42 next update check in 13338s (daily at 4:00 Europe/Moscow)
server listening on http://0.0.0.0:4096
```

Открой `http://localhost:4096`. Браузер спросит логин и пароль: логин `opencode`, пароль из `OPENCODE_SERVER_PASSWORD`.

## Рабочая папка: несколько репозиториев в одном контейнере

Контейнер обслуживает рабочую папку, а не один репозиторий. Это папка на хосте, в которой лежит один репозиторий или несколько. Она задаётся переменной `WORKSPACE`. Проекты внутри переключаются в веб-интерфейсе одного сервера: открываешь проект через пикер папок, и сессии, терминал и конфиг проекта привязываются к его директории. Порт один, зависимости и логин в провайдерах общие.

Рабочая папка должна быть узкой. Внутри неё изоляции между репозиториями нет: агент, которому прилетела инъекция в репозитории A, пишет в код и в `.git` репозитория B и читает ssh-ключ. Проверка путей в opencode (`external_directory`) ловит промах честного агента, но не инъекцию: команды в shell она почти не разбирает. Поэтому клади в одну рабочую папку только репозитории одного уровня доверия. Рабочие и личные репозитории разводи по разным рабочим папкам, то есть по разным контейнерам. Если рабочая папка совпадает с репозиторием, это обычный частный случай. Подробности в `docs/adr/0005-container-per-workspace-folder.md`.

Чтобы поднять второй контейнер для другой рабочей папки, склонируй харнесс второй раз и запусти визард в каждой копии: у каждой свой `.env`, свой override и свой ssh-ключ.

Копии не мешают друг другу, потому что у каждой рабочей папки свой compose-проект. Визард выводит его имя из `WORKSPACE` и пишет в `.env` строкой `COMPOSE_PROJECT_NAME` вида `opencode-<хвост пути>-<контрольная сумма>`. Порт он тоже выводит из пути, в диапазоне 4097-4996, так что вторая рабочая папка не упирается в занятый 4096. Порт считается как контрольная сумма пути, поэтому у двух папок он изредка совпадает. Проверка порта в визарде поймает это, только если чужой контейнер запущен; тогда выбери другой порт в визарде. Образ свой у каждого проекта (`opencode-server:<имя проекта>`), поэтому пересборка с другим тулчейном не подменяет образ соседу. Без визарда проект называется `opencode`, как раньше. Повторный запуск визарда для той же рабочей папки имя проекта и порт не меняет, даже если `.env` настроен до появления `COMPOSE_PROJECT_NAME`: такая папка остаётся проектом `opencode`.

Если в той же копии сменить `WORKSPACE` через визард, старый контейнер продолжит работать, а `docker compose` в этой папке начнёт управлять новым. Остановить старый можно так: `docker compose -p <старое имя проекта> down`.

Появился новый питон-проект в рабочей папке (склонировал репозиторий или завёл `pyproject.toml`): перезапусти визард. Он найдёт питон-проект и даст ему свой `.venv`-volume. Пока этого не сделано, у нового питон-проекта контейнерный `.venv` не отделён от хостового.

Саму рабочую папку нельзя делать git-репозиторием, если внутри неё лежат другие репозитории: из-за бага opencode #51191 сессии из подпапки уезжают в корень внешнего репозитория. Визард предупреждает об этом. Выбери папку на уровень выше или вынеси вложенные репозитории.

Домашняя папка контейнера своя у каждой рабочей папки: визард пишет в `.env` строку `HOME_VOLUME` вида `opencode-home-<хвост пути>-<контрольная сумма>`. Агент пишет в домашку, там лежат бинарь opencode и `~/.local/bin`. Общая домашка позволила бы агенту из одного репозитория подложить `git` или подменить бинарь так, что код запустится в контейнере другого репозитория с его deploy-ключом (ADR 0004).

Цена: в каждой рабочей папке надо один раз залогиниться в провайдерах и один раз скачать бинарь. Если ты обновляешь настроенный раньше харнесс, визард при следующем запуске переведёт репозиторий на новую домашку и предупредит об этом; старая общая `opencode_opencode-home` останется в Docker нетронутой. В ней могла остаться подложенная закладка и лежат токены всех провайдеров, так что когда все репозитории перейдут, считай её недоверенной и удали: `docker volume rm opencode_opencode-home`. Оставить общую можно, прописав в `.env` `HOME_VOLUME=opencode_opencode-home`: визард такое значение не трогает. Тогда агент в одном репозитории может подложить код для всех остальных, так что делай это только для репозиториев, которым доверяешь одинаково. Без визарда `HOME_VOLUME` по умолчанию тоже общий, задай своё имя на репозиторий.

Что это даёт по мелочам:

- история сессий у каждой рабочей папки своя;
- `docker compose down -v` удаляет volume этой рабочей папки: домашку (логин и бинарь придётся получить заново) и все `.venv`-volume питон-проектов. Чтобы сбросить только один `.venv`, удали его volume руками: `docker volume rm <имя volume>`; имена лежат в `docker-compose.override.yml`.

## Провайдеры моделей

В `opencode.jsonc` лежат настройки провайдеров: адреса, заголовки, модели. Ключи и OAuth-токены провайдеров opencode v2 хранит в своей базе (`~/.local/share/opencode/opencode.db`), и с хоста они не подтянутся. Если ключ подключён в конфиге через `{file:...}` из папки конфига, он работает и в контейнере. Ключ через `{env:...}` заработает, только если добавить эту переменную в `environment` в `docker-compose.override.yml`: переменные хоста в контейнер сами не попадают. Иначе подключи провайдера один раз прямо в веб-интерфейсе, там же проходит и OAuth. Команда в контейнере для этого не нужна.

Логин сохраняется в домашнем volume рабочей папки (`HOME_VOLUME`) и переживает перезапуски и обновления. В другой рабочей папке логиниться придётся заново, подробности в разделе про рабочую папку.

Любую команду opencode внутри контейнера запускай с `--server http://127.0.0.1:4096`. Без этого флага CLI поднимет второй, фоновый сервер со своими настройками.

## Git-доступ

Чтобы агент делал `git push` из контейнера, нужен ключ без passphrase: ssh-agent в контейнере нет, ввести passphrase некому. Не бери для этого свой личный ключ. Заведи отдельный deploy-ключ:

```sh
ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_deploy
```

Ключ один на всю рабочую папку. Публичную часть `~/.ssh/id_deploy.pub` добавь в GitLab в каждом проекте, куда агент должен пушить: в проекте `Settings > Repository > Deploy keys`, с галочкой `Grant write permissions`. Без неё push отвергнут.

Визард (стадия «Git-доступ по SSH») показывает приватные ключи из `~/.ssh`. Если на выбранном стоит passphrase, он не даёт его взять и возвращает к выбору ключа: пропустить стадию можно, введя `-`. Путь к ключу он делает абсолютным и отвергает пути с `"`, `\`, `$`, `:` и переводами строк, иначе они ломают mount. Ключ внутри рабочей папки он тоже не берёт: агент подменил бы его ссылкой на любой файл хоста. Хосты он берёт из remote всех репозиториев рабочей папки (на любой глубине; из remote берётся `origin`, а если его нет, первый) и собирает known_hosts через `ssh-keyscan`. Хост, общий для нескольких репозиториев, подтверждается один раз. Тут нужно сверить fingerprint с тем, что публикует провайдер или говорит админ сервера: знакомство с хостом без сверки не защищает от подмены. known_hosts лежит в `.git-ssh/` (она в `.gitignore`). Ключ и known_hosts монтируются в контейнер только на чтение, git ходит ими через `GIT_SSH_COMMAND` (с `BatchMode=yes`: если ключ не подошёл, git падает сразу, а не ждёт ввода). `~/.gitconfig` хоста не мешает.

В `.env` визард пишет `GIT_SSH_COMMAND` только после того, как записал `docker-compose.override.yml` с mount ключа. Если ты отказался перезаписать override, старая настройка остаётся как была, а в итоговом списке появится строка, что ssh-изменение не применено.

Когда сервер поднялся, визард делает из контейнера `git push --dry-run` по разу на каждый ssh-хост из known_hosts: из первого репозитория, который пушит на этот хост. Хосты, которых нет в known_hosts, он не проверяет, они уже стоят в итоговом списке недоделанного. Если проверять нечего, визард пишет почему. Ошибка push не останавливает визард, это только проверка.

Визард перечисляет ssh-remote всех репозиториев и напоминает добавить ключ в каждый GitLab-проект, но не проверяет, что он там есть. Если в рабочей папке нет ни одного репозитория с ssh-remote или ни один хост не попал в known_hosts, стадия падает. Повторный запуск не пересканирует хосты, которые уже лежат в `.git-ssh/known_hosts`, а спрашивает только про новые; хосты, которых больше нет ни в одном remote, из файла уходят. Если ключ хоста сменился, старая запись остаётся и push падает: удали `.git-ssh/known_hosts` и перезапусти визард.

Поддержан только push по ssh. Remote по https визард пропускает. Remote через псевдоним из `~/.ssh/config` (`git@gl-work:group/repo.git`) тоже не поддержан: в контейнере этого конфига нет, и псевдоним там не разрешится. Визард узнаёт такой remote через `ssh -G`, печатает готовую команду `git -C <репозиторий> remote set-url ...` с настоящим хостом и пропускает этот репозиторий. Репозиторий без remote он тоже пропускает с сообщением.

## Тулчейн проекта

В образе есть только то, что нужно самому opencode: git, curl, ripgrep. Чтобы агент собирал проект и гонял тесты, нужен ещё тулчейн проекта.

Для питона есть профиль, его включает визард (`INSTALL_UV=1` в `.env`): `uv` ставится прямо в образ. Его ставит pip в отдельной стадии сборки, в образ попадает только бинарь `uv`, а pip и питон этой стадии остаются за бортом. Версия и хэши колёс закреплены в `docker/uv-requirements.txt`. Компилятор `build-essential` визард подставляет как значение `EXTRA_APT_PACKAGES` по умолчанию. Системного питона в образе нет: нужную версию приносит `uv sync`. Dev-библиотеки для нативных зависимостей допиши в `EXTRA_APT_PACKAGES`, например `build-essential libpq-dev libffi-dev`, и пересобери образ.

Обновить uv в образе:

```sh
make bump-uv UV_VERSION=0.14.0
docker compose up -d --build
```

Первая команда перезаписывает `docker/uv-requirements.txt`: новая версия и sha256 всех её файлов с PyPI. Ей нужен uv на хосте. Если версии нет на PyPI, команда падает, а прежний файл остаётся как был. Закоммить файл вместе с остальным: его читает сборка.

У контейнера свой `.venv`: отдельный volume смонтирован поверх `.venv` каждого питон-проекта. Хостовый venv собран под macOS и в Linux бесполезен, поэтому контейнер его не видит и не перезаписывает, а твой `uv sync` на хосте не ломает контейнерный. Визард находит питон-проекты: папки на любой глубине рабочей папки, где лежит `pyproject.toml`, а выше внутри рабочей папки другого `pyproject.toml` нет. `.git`, `.venv` и `node_modules` он не обходит. Список питон-проектов визард показывает на стадии образа и ещё раз в самом конце, каждому даёт свой volume. Volume'ы и точки монтирования он пишет в `docker-compose.override.yml`, а сборке передаёт список точек через аргумент `VENV_MOUNT_POINTS`, чтобы образ создал их с владельцем opencode.

Появился новый питон-проект: перезапусти визард, иначе у него нет своего `.venv`-volume и контейнерный `uv sync` пишет в хостовый `.venv`. Если на повторном запуске питон-проекты пропадают из override, визард перечисляет их до вопроса о перезаписи. Не убирал их сам — ищи `pyproject.toml` над ними, например в корне рабочей папки.

На хосте в каждом питон-проекте остаётся пустая папка `.venv`: это точка монтирования. Визард создаёт недостающие сам. Без визарда контейнерный `.venv` не отделён от хостового: сделай `mkdir .venv` в питон-проекте и опиши volume в `docker-compose.override.yml` по образцу из `docker-compose.override.yml.example`. Иначе на Linux Docker создаст папку от root. Подробности в `docs/adr/0003-container-venv-isolated-from-host.md`.

Для остальных стеков перечисли системные пакеты в `EXTRA_APT_PACKAGES` в `.env` и пересобери образ:

```sh
EXTRA_APT_PACKAGES=build-essential libpq-dev
```

В домашнюю папку агент может ставить что угодно (`nvm`, Python через `uv python install`, свои бинарники). Она лежит в volume `HOME_VOLUME` этой рабочей папки, поэтому установленное переживает перезапуски и обновления. У другой рабочей папки свой volume и своя установка.

## Корпоративная сеть

Если `deb.debian.org` закрыт и пакеты идут через внутреннее зеркало, визард спросит папку с apt-настройками зеркала и скопирует их в `docker/apt/`. Туда же их можно положить руками. Файлы `*.sources` и `*.list` заменяют стандартные источники Debian, `*.conf` ложатся в `apt.conf.d` (прокси, логин, `CAInfo`), `*.crt` становятся доверенными сертификатами в образе. Формат и пример лежат в `docker/apt/README.md`. Всё, кроме README, в `.gitignore`, так что адреса зеркала в репозиторий не попадут.

`*.conf` действуют только во время сборки и в образ не попадают, так что логин и прокси зеркала не оседают в его слоях. Поэтому логин клади в `*.conf`, а не в адрес внутри `*.sources`: источники и сертификаты в образе остаются. Обратная сторона: `apt-get install` руками внутри запущенного контейнера в корпоративной сети до зеркала не достучится. Нужные пакеты добавляй через `EXTRA_APT_PACKAGES` в `.env` и пересобирай образ.

Базовый образ берётся из `BASE_IMAGE`. Если Docker Hub закрыт, укажи в `.env` образ из внутреннего registry.

uv в питон-профиле pip берёт из PyPI-индекса `UV_PIP_INDEX_URL`, по умолчанию `https://pypi.org/simple`. Если pypi.org закрыт, визард спросит адрес корпоративного индекса, например `https://nexus.example.corp/repository/pypi/simple`. Нужен только https-адрес без логина: http pip не примет, а логин и пароль в адресе визард отклонит. Хэши в `docker/uv-requirements.txt` закрепляют ровно те файлы uv, что опубликованы на PyPI под этой версией, так что индекс с подменённым uv сборку уронит. pip доверяет корпоративным `*.crt` из `docker/apt`, а `python3-pip` для стадии идёт через то же apt-зеркало. Прокси из apt-шных `*.conf` pip не видит: если индекс доступен только через прокси, задай его для сборок в `~/.docker/config.json`, как описано ниже в разделе про прокси. Адрес индекса виден только стадии с pip, в истории готового образа его нет.

Без питон-профиля (`INSTALL_UV=0`) стадия с pip не собирается вовсе, и индекс сборке не нужен.

### Прокси для контейнера

Без прокси контейнер не скачает opencode с opencode.ai и не достучится до провайдеров: compose не передаёт `HTTPS_PROXY`. Править compose не нужно. Docker сам подставляет прокси в контейнеры и сборки из клиентского конфига `~/.docker/config.json`:

```json
{
  "proxies": {
    "default": {
      "httpProxy": "http://proxy.example.com:3128",
      "httpsProxy": "http://proxy.example.com:3128",
      "noProxy": "localhost,127.0.0.0/8,.example.org"
    }
  }
}
```

Конфиг подхватывается без перезапуска Docker, но только для новых контейнеров и сборок. После правки пересобери образ и пересоздай контейнер: `docker compose up -d --build`. Логин и пароль в адресе прокси попадут в переменные окружения контейнера открытым текстом, их видно через `docker inspect`. Эти настройки работают только внутри контейнеров: для самого демона Docker (скачивание образов) прокси задаётся отдельно. Описание: https://docs.docker.com/engine/cli/proxy/.

## Обновления

В 4:00 по `TZ` контейнер сверяет установленную версию с последней. Если вышла новая, он ставит её и перезапускается сам. Если версия та же, ничего не происходит. Час задаёт `OPENCODE_UPDATE_HOUR`. Перезапуск обрывает агента, если тот в этот момент работает.

Проверить и обновить руками:

```sh
docker compose exec opencode opencode-update check
docker compose restart
```

## Что контейнер не защищает

Контейнер не песочница против скомпрометированного агента, если ты запускаешь git на хосте. Агент пишет во всю рабочую папку, включая `.git/` каждого репозитория. Через `core.fsmonitor`, `core.hooksPath`, `.git/hooks` или файл `.git/commondir` он заставляет хостовый git (IDE, промпт шелла) выполнить его команды при любом `git status`. Я проверил это на git 2.55.0 с Docker. То же работает для вложенного репозитория, который агент создаёт в подпапке.

Для git относись к контейнеру так, будто агент работает прямо на хосте. После сессий с недоверенным входом смотри `.git/config` и хуки, а пока агент обрабатывает недоверенный ввод, не запускай хостовые git-инструменты в рабочей папке.

Отдельно про рабочую папку из нескольких репозиториев:

- Между репозиториями внутри неё границы нет. Инъекция в репозитории A пишет в код и `.git` репозитория B и читает deploy-ключ из `/run/git-ssh/id`. Одна утечка открывает все репозитории, где этот ключ подключён, поэтому заводи ключ на рабочую папку и держи в ней репозитории одного уровня доверия.
- Конфиги в промежуточных папках. opencode ищет `.opencode`, `.claude`, `.agents` и `opencode.json` вверх по дереву до `/`, а хостовый Claude Code так же собирает `CLAUDE.md`. Агент может положить такой файл в папку между рабочей папкой и репозиторием, которая не входит ни в один репозиторий и потому не видна ни в одном `git diff`. Это побег на хост того же класса, что через `.git`. Смотри такие файлы в промежуточных папках после недоверенных сессий.
- Shell в обход `external_directory`. Эта проверка смотрит пути инструментов `edit`, `write` и `read`, а в shell только cwd и аргументы `cd` и `pushd`. `echo >> ../B/.git/config` или `python -c` проходят без вопроса, так что ограничение по папке в opencode границей доверия не считай.
- Рабочая папка с вложенными репозиториями не должна быть git-репозиторием сама (opencode #51191, подробности выше).

Харнесс, то есть этот репозиторий с compose-файлами, `scripts/setup.sh`, `.git-ssh/known_hosts` и `.env`, не должен лежать в рабочей папке, а рабочая папка в нём. Иначе агент перепишет то, что хост выполнит на следующем `up`. Визард такую рабочую папку не принимает, как и ssh-ключ внутри неё; без визарда следи за этим сам.

Решение про отдельный клон для агента ждёт тебя: `.scratch/agent-containment/issues/01-host-git-escape-via-dotgit.md`.

## Тонкие места

- Абсолютные симлинки в `~/.config/opencode` (например, `plugins -> ~/dotfiles/...`) в контейнере никуда не ведут. Контейнер перечисляет их при старте строками `warning: broken symlink`. Цель такой ссылки надо смонтировать по тому же пути, пример лежит в `docker-compose.override.yml.example`. Туда же можно добавить глобальные скиллы из `~/.agents`.
- `127.0.0.1` и `localhost` в конфиге opencode внутри контейнера означают сам контейнер. Если провайдер или MCP ходит в локальный прокси на хосте, впиши его порт в `HOST_LOOPBACK_PORTS` в `.env` (визард находит такие порты в конфиге сам). Контейнер пробросит `localhost:<порт>` на тот же порт хоста, и конфиг менять не придётся.
- `include` и `includeIf` в `~/.gitconfig` ссылаются на файлы, которых в контейнере нет. Если git в контейнере не знает `user.name`, смонтируй эти файлы через override.
- На Linux-хосте поставь в `.env` `OPENCODE_UID` и `OPENCODE_GID` из `id -u` и `id -g`, иначе файлы в репозитории будут принадлежать чужому пользователю. На маке это не нужно.
