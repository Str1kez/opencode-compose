# Что контейнер не защищает

Контейнер не песочница против скомпрометированного агента, если ты запускаешь git на хосте. Агент пишет во всю рабочую папку, включая `.git/` каждого репозитория. Через `core.fsmonitor`, `core.hooksPath`, `.git/hooks` или файл `.git/commondir` он заставляет хостовый git (IDE, промпт шелла) выполнить его команды при любом `git status`. Я проверил это на git 2.55.0 с Docker. То же работает для вложенного репозитория, который агент создаёт в подпапке.

Для git относись к контейнеру так, будто агент работает прямо на хосте. После сессий с недоверенным входом смотри `.git/config` и хуки, а пока агент обрабатывает недоверенный ввод, не запускай хостовые git-инструменты в рабочей папке.

## Рабочая папка из нескольких репозиториев

- Между репозиториями внутри неё границы нет. Инъекция в репозитории A пишет в код и `.git` репозитория B и читает deploy-ключ из `/run/git-ssh/id`. Одна утечка открывает все репозитории, где этот ключ подключён, поэтому заводи ключ на рабочую папку и держи в ней репозитории одного уровня доверия.
- Конфиги в промежуточных папках. opencode ищет `.opencode`, `.claude`, `.agents` и `opencode.json` вверх по дереву до `/`, а хостовый Claude Code так же собирает `CLAUDE.md`. Агент может положить такой файл в папку между рабочей папкой и репозиторием, которая не входит ни в один репозиторий и потому не видна ни в одном `git diff`. Это побег на хост того же класса, что через `.git`. Смотри такие файлы в промежуточных папках после недоверенных сессий.
- Shell в обход `external_directory`. Эта проверка смотрит пути инструментов `edit`, `write` и `read`, а в shell только cwd и аргументы `cd` и `pushd`. `echo >> ../B/.git/config` или `python -c` проходят без вопроса, так что ограничение по папке в opencode границей доверия не считай.
- Рабочая папка с вложенными репозиториями не должна быть git-репозиторием сама ([opencode #51191](workspace.md#рабочая-папка-не-должна-быть-git-репозиторием)).

## Харнесс и рабочая папка

Харнесс, то есть этот репозиторий с compose-файлами, `scripts/setup.sh`, `.git-ssh/known_hosts` и `.env`, не должен лежать в рабочей папке, а рабочая папка в нём. Иначе агент перепишет то, что хост выполнит на следующем `up`. Визард такую рабочую папку не принимает, как и ssh-ключ внутри неё. Разбор с примерами атак и что делать, если визард отказал: [рабочая папка](workspace.md#харнесс-не-может-лежать-в-рабочей-папке).

## Домашка контейнера

Домашка своя у каждой рабочей папки, потому что агент в неё пишет. Общая домашка между рабочими папками разного доверия — дыра того же класса: агент подменит бинарь, и код запустится в соседнем контейнере с его ключом ([подробности](workspace.md#домашняя-папка-контейнера)).
