# Спека: движок-agnostic визард + рабочий git push (этап 1 / MVP)

Связанные решения: [ADR 0001](../adr/0001-engine-agnostic-colima-default.md), [ADR 0002](../adr/0002-one-container-per-repo.md).

## Problem Statement

Я гоняю opencode в контейнере, потому что MDM убивает бинарь на маке. Сейчас харнесс завязан на один движок: визард проверяет только Docker Desktop/OrbStack, а на рабочей машине OrbStack сам нестабилен под jamf. Я раздаю проект коллегам, у которых стек разный, и у них визард упрётся в предположение о движке. Вдобавок агент внутри контейнера коммитит локально, но запушить не может — ssh-кредов внутри нет, и человек узнаёт об этом, только когда push молча не срабатывает.

## Solution

Визард работает с любым движком: детектит colima, OrbStack или Docker Desktop и поднимает харнесс поверх любого из них. colima рекомендован как дефолт для раздачи. При colima визард проверяет, что WORKSPACE примонтирован в VM, и подсказывает команду, если нет.

Git push заводится из коробки. Визард сканирует `~/.ssh`, даёт выбрать ключ, проверяет на нём passphrase и предупреждает, собирает known_hosts через `ssh-keyscan` с показом fingerprint на сверку, монтирует ключ read-only и направляет git через `GIT_SSH_COMMAND`. Остаёмся на модели один репозиторий — один контейнер.

Для питон-проектов контейнер получает собственный `.venv` через volume поверх `WORKSPACE/.venv`, не конфликтуя с хостовым, а визард предлагает питон-профиль поставки: `build-essential` и uv в образ, без системного питона.

## User Stories

1. Как владелец харнесса, я хочу, чтобы визард сам определил, какой Docker-движок у меня стоит, чтобы не прописывать это руками.
2. Как владелец харнесса на corporate-маке, где OrbStack нестабилен, я хочу поднять харнесс на colima, чтобы не зависеть от движка, который жрёт jamf.
3. Как коллега, разворачивающий харнесс у себя, я хочу, чтобы визард работал с тем движком, что уже есть на моей машине, чтобы не ставить новый софт без нужды.
4. Как коллега без установленного движка, я хочу, чтобы README рекомендовал colima и объяснял установку, чтобы начать с понятного дефолта.
5. Как владелец харнесса на colima, я хочу, чтобы визард проверил, виден ли WORKSPACE внутри VM, чтобы bind по тому же пути не упёрся в пустоту.
6. Как владелец харнесса на colima, я хочу получить точную команду `colima start --mount ...`, если моего репозитория нет в mount, чтобы не гадать, почему контейнер не видит файлы.
7. Как владелец харнесса, у которого colima уже поднят с чужими контейнерами, я хочу, чтобы визард предупредил, что добавление mount требует рестарта colima и оборвёт эти контейнеры, чтобы я не потерял их молча.
8. Как агент внутри контейнера, я хочу иметь рабочий ssh-доступ к remote, чтобы пушить ветки и открывать PR, а не только коммитить локально.
9. Как владелец харнесса, я хочу выбрать в визарде конкретный ssh-ключ из `~/.ssh`, чтобы в контейнер попал ровно тот, что я указал, а не весь каталог.
10. Как владелец харнесса, я хочу, чтобы визард предупредил меня, если на выбранном ключе стоит passphrase, потому что без ssh-agent в контейнере такой ключ молча не заведётся.
11. Как коллега, я хочу, чтобы визард прямым текстом сказал завести deploy-ключ без passphrase и добавить его в GitLab, чтобы не монтировать ключ, которым push не пройдёт.
12. Как владелец харнесса, я хочу, чтобы мой ssh-ключ монтировался только на чтение, чтобы контейнер не мог его изменить.
13. Как владелец харнесса, я хочу, чтобы git внутри контейнера использовал именно указанный ключ и known_hosts, не трогая смонтированный read-only `.gitconfig`, чтобы обойти мои `include`/`includeIf` на файлы, которых в контейнере нет.
14. Как владелец харнесса, я хочу, чтобы визард сам вытащил remote из `.git/config` репозитория и собрал known_hosts, чтобы не делать это руками.
15. Как владелец харнесса, я хочу видеть fingerprint хоста, который визард получил через keyscan, и сверить его, чтобы не поймать MITM на доверии вслепую.
16. Как коллега, который жмёт Enter не глядя, я хочу, чтобы шаг со сверкой fingerprint был явным, чтобы случайно не принять чужой ключ хоста.
17. Как владелец харнесса, я хочу, чтобы `.env` и сгенерированные файлы с путями к ключу и known_hosts не попадали в git, чтобы не утекли машинно-специфичные настройки.
18. Как владелец харнесса, я хочу проверить, что push реально проходит из контейнера, сразу после настройки, чтобы не узнать о поломке в момент, когда она срочно нужна.
19. Как владелец харнесса, перезапускающий визард, я хочу, чтобы уже выбранный движок, ключ и хост предлагались по Enter, чтобы не вводить всё заново.
20. Как разработчик питон-проектов, я хочу, чтобы контейнер не трогал мой хостовый `.venv` и не ломался об него, потому что он собран под macOS и в Linux нерабочий.
21. Как разработчик, я хочу, чтобы `.venv`, созданный внутри контейнера, не перезаписывал мой рабочий `.venv` на хосте, чтобы я не потерял хостовое окружение.
22. Как разработчик, я хочу, чтобы `.venv` в контейнере лежал на стандартном пути, чтобы прямой вызов `.venv/bin/python` и обычные команды работали без спецнастройки.
23. Как разработчик, я хочу, чтобы визард отдельным шагом предлагал питон-профиль поставки (`build-essential` и uv в образ), чтобы `uv sync` собирал колёса из коробки.
24. Как разработчик, я хочу, чтобы в образ не ставился системный питон, который проекту не нужен, потому что uv притащит свой при `uv sync`.
25. Как разработчик проекта с нативными зависимостями, я хочу дописать свои dev-библиотеки (libpq-dev, libffi-dev), чтобы тяжёлые колёса компилировались, а не падали на первом `uv sync`.
26. Как коллега, я хочу, чтобы дефолтный набор пакетов не тащил лишний `python3-dev`, чтобы образ не нёс ненужного.

## Implementation Decisions

**Детект движка.** Визард определяет доступный движок (проверка `docker context`, наличие `colima`, ответ `docker info`) и ветвит поведение. compose сам по движку не ветвится — он работает поверх любого docker-совместимого сокета, вся движок-специфика живёт в визарде и README.

**colima lifecycle.** Если выбран colima и он не запущен или поднят без WORKSPACE в mount, визард печатает точную команду `colima start --mount $WORKSPACE:w` и просит выполнить. Автостарт и тем более рестарт colima визард делает только с явного подтверждения и предупреждает, что `colima stop && start` оборвёт остальные контейнеры пользователя. Втихую VM не трогает.

**Выбор ssh-ключа.** Визард сканирует `~/.ssh`, показывает приватные ключи, даёт выбрать один. На выбранном ключе проверяет наличие passphrase (`ssh-keygen -y -P "" -f <key>` без ошибки = без пароля) и, если пароль есть, предупреждает и советует deploy-ключ без passphrase. Ключ коллеги не хардкодится — выбор каждый раз.

**Направление git на ключ.** Через переменную окружения в compose:
`GIT_SSH_COMMAND="ssh -i <key> -o IdentitiesOnly=yes -o UserKnownHostsFile=<known_hosts>"`.
Это не трогает read-only `.gitconfig`, обходит проблему `include`/`includeIf` и переносимо на машины коллег. Покрывает git-операции (push/pull/fetch); голый `ssh`/`scp` в обход git сознательно вне покрытия.

**Монтирование ключа и known_hosts.** Выбранный ключ монтируется в контейнер read-only. known_hosts визард собирает так: берёт remote из `WORKSPACE/.git/config`, выделяет хост, делает `ssh-keyscan`, показывает fingerprint и просит сверить, кладёт результат в gitignored-файл проекта и монтирует его read-only.

**Питон-тулчейн и изоляция `.venv`.** См. [ADR 0003](../adr/0003-container-venv-isolated-from-host.md). Отдельный volume монтируется поверх `WORKSPACE/.venv`: хостовый venv не протекает в контейнер, контейнерный не пишется на хост, путь остаётся стандартным. Визард отдельным шагом предлагает питон-профиль: `build-essential` (gcc для колёс) и uv в образ. Системный питон и `python3-dev` не ставим — uv приносит standalone-питон с заголовками при `uv sync`. uv ставится отдельным шагом Dockerfile, а не через `EXTRA_APT_PACKAGES` (uv не apt-пакет). Дефолт `EXTRA_APT_PACKAGES` меняю: убираю `python3-dev`, базовый профиль — `build-essential`. Профиль — стартовый набор плюс поле «допиши dev-пакеты проекта»; визард их не угадывает.

**Границы неизменного.** Модель один WORKSPACE на контейнер, read-only конфиги хоста, ежедневное автообновление, basic auth, проброс `HOST_LOOPBACK_PORTS` — остаются как есть. Этот этап добавляет движок-детект, git-доступ и питон-тулчейн, не переписывает существующее.

## Testing Decisions

Хороший тест здесь проверяет внешнее поведение харнесса, а не внутренности bash-функций: сервер поднялся и отвечает, движок задетектился, git push из контейнера прошёл. Детали реализации функций визарда не фиксируем тестами — они будут меняться.

Риск этапа — low-medium: это bash и инфраструктурная обвязка, где отказ ограничен и обратим. По стандартам проекта юнит-тесты на каждую функцию не плодим.

- **Главный шов — один интеграционный смоук:** поднять харнесс (`docker compose up -d --build` либо визардом), дождаться ответа сервера, из контейнера сделать push в тестовый remote и проверить, что он прошёл. Это высшая точка, где поведение наблюдаемо целиком.
- **Дешёвые статические проверки:** `shellcheck` на `scripts/setup.sh` и `docker/entrypoint.sh`.
- **Прошлый арт:** в compose уже есть healthcheck сервера, в визарде — `wait_until_ready`. Смоук опирается на них, новых seam не вводит.

## Out of Scope

- dind-сайдкар для системных тестов проекта — этап 2, проектируется отдельно (TLS-vs-plain сокет, `network_mode: service:dind` против `DOCKER_HOST=tcp://dind`).
- Мультипроект в одном сервере — см. ADR 0002.
- HTTPS-токены для git: на старте только SSH, у всех ключи уже есть.
- SSH agent forwarding в контейнер: на маке `SSH_AUTH_SOCK` — launchd-сокет, в Linux-контейнер напрямую не прокидывается; сознательно не делаем.
- Любая подстройка харнесса под обход MDM-агента — см. ADR 0001.
- Автоопределение нативных dev-зависимостей проекта: визард не парсит `pyproject.toml`, пользователь вписывает dev-библиотеки сам.

## Further Notes

На jamf-маке стабильность харнесса я не гарантирую ничем из этой спеки: если security-агент рубит сокет движка, движок-детект это не чинит. Путь к стабильности — allowlist бинаря opencode через IT. Диагностику лога (чем и когда убивается процесс движка) могу снять под заявку, но это диагностика для IT, а не обход.

Главный подводный камень раздачи коллегам — colima mount. На OrbStack bind по тому же пути бесплатный, на colima его надо явно прокинуть в VM. Визард это закрывает, README — объясняет.
